钟澄文献检索方法论

检索方案设计与检索问题诊断

源自钟澄《科研论》的检索经验：鲸吞法先吞后吐、概念拆分到最小单元、 万能检索式行内 OR 行间 AND、小步进实测、完成比完美。 它解决的不是"用哪个数据库"，而是"搜什么、怎么构造、怎么判断够不够"。

在 GitHub 上查看 安装方法 TDD 证据

01万能检索式

整套方法的地基。括号的含义是"这些词出现在搜索引擎的同一行"——中英文引擎都是这样。

(
A1ORA2ORA3
) AND (
B1ORB2ORB3
)
OR —— 行内，只连同一个检索词的同义表达 AND —— 行间，只连不同的检索词

「所以我强烈建议采用我说的这种简单的检索式，我自己测试了几个检索案例，全都是适合这种模式的。」

为什么一行里不得同时出现 AND 和 OR

检索式逻辑一复杂，搜太多或搜不到时你无法判断是哪一部分的问题。简单结构让每一轮测试只改一个变量，问题立刻可定位。

演进不一次性交付成品

A → A AND B → A AND (A1 OR A2) AND (B1 OR B2)。和写程序一样：一次不要码太多代码，出问题才能马上排查。

02五条原则

检索式设置属于搜商，是后续一切工作的起点。总耗时最多一天；因"差不多不就行了"导致检索式不完善，后期浪费的时间以年计。

一鲸吞法：先吞后吐

第一轮尽可能囊括相关文献，精准靠分组解决，不靠第一轮提纯。筛选标准、纳入排除标准属于【吐】，必须后置于分组。

二概念拆分到最小单元

作者研究 A 却从不提及 A——研究甲基铵铅碘的论文标题里没有 perovskite。拆开后只需掌握每个单元的同义表达，不必掌握组合后词组的同义表达。

三万能检索式

(A1 OR A2) AND (B1 OR B2)，行内只用 OR，行间只用 AND。

四小步进实测

先测 A → 过多则 A AND B → 再逐步扩充同义表达。每个候选词组都回引擎测量级，不凭直译想当然。

五完成比完美

90%+ 覆盖即启动；但也不因少量文献就开始研究——基于少量文献开展研究，未来走一年以上弯路并不稀奇。

03"够用"的判据

用户说"文献看不完 / 不够"时，先问是哪个用途不够，再对上表。对上表能解决的，不需要任何新检索。

用途篇数
形成语料库、完成写作15~20 篇
写作文字素材库≤ 50 篇
【验】字诀验证 idea几篇~十几篇
初步往下推进> 50~100 篇
不必穷尽浏览> 1000 篇
启动相关度 / 覆盖度>40% / 90%+

「鲸吞 ≠ 吃完。只要有适当的样本量已经可以反映全局特点了，在样本量过大的情况下，我们没必要穷尽索引每一个样本……只要能吃饱（也就是达成我们的目的）就行了。」

04八条铁律

前五条管检索式，后三条管"什么不能外包给工具"。

  1. 行内只用 OR，行间只用 AND，一行里不得同时出现两者。
  2. 所有符号半角——通配符、双引号、括号。
  3. 先吞后吐。筛选标准、纳入排除标准是【吐】，必须后置于分组。
  4. 小步进。不一次性交付成品检索式；每轮只改一个变量并记录命中数。
  5. 形成记录。每个检索式都留下 序号-数据库 | 完整检索式 日期。
  6. 不用 AI 批量摘要替代分组。分组中的判断正是 idea 来源；"能分出组"和"能分出为你后续研究和论文发表提供参考的分组"是完全不同的概念。
  7. 不用词频统计 / 共现网络工具（VOSviewer、CiteSpace、biblioshiny）代替人工分组。它们搜不到 @、like、nano 这类关键符号与词干，且会把同义表达割裂成不同组。
  8. 开展具体工作前必做钓鱼法测试——确认没有与 idea 完全重合的报道。

05两个模式

同一个 skill，两条入口。都通向：入库 → 分组 → 查漏。

设计模式 · 8 步

① 明确终点（出 idea / 验证 idea / 写作素材）② 概念拆分到最小单元 ③ 同义表达四渠道 ④ 组装万能检索式 ⑤ 小步进实测 ⑥ 入库与形成记录 ⑦ 分组规划 ⑧ 查漏与推进阈值。

诊断模式 · 7 问

① 相关度（>40% 即启动）② 检索式结构 ③ 同义表达在穷尽还是已保留最小单元 ④ 符号半角 / TOPIC 误写成 TITLE ⑤ 字段策略 ⑥ 单侧命中数量级 ⑦ 下一轮只改一个变量。

症状根因处方
结果太多行内 AND 行间 OR 混杂；缺限定词简化为 (A) AND (B)；删除测试
结果太少或 0直译词；同义表达缺失；全角符号四渠道补表达；每个词组回引擎测量级
一半不相关这是正常的，不是缺陷>40% 即启动，靠分组求值
同义词永远穷尽不完穷尽思维保留最小单元 + 启动支点论 + 增量更新
4000 篇看不完缺分组，不是缺速度鲸吞法分组路线 + 阈值表
搜不到，怀疑是空白检索词选错（该搜 B 不是 A）先怀疑检索词；单侧命中数验证法

07它是被测试逼出来的

按 writing-skills 的 TDD 纪律开发：先写压力场景 → 无 skill 跑 RED 基线 → 带 skill 跑 GREEN → 从 GREEN 结果反推缺口做 REFACTOR。

1 / 15 RED 基线通过（无 skill）
→
15 / 15 GREEN 通过（带 skill，首轮）
场景压力RED 失败模式GREEN
S1 设计 无检索基础 + 时间压力 + 导师催 堆词组 + 综述方法论：查准率 / 召回率 / PRISMA-ScR 漏斗 / 引文滚雪球 / 核心作者核心期刊清单 6/6
S2 诊断 同义词穷尽焦虑 + 结果过载 + AI 摘要诱惑 开头两句是对的，随后滑回"查准率崩塌 / 特异性 0.5 / 种子论文测召回"，并给出"六条可辩护协议"给 AI 开 conditional 许可 5/5
S3 边界 文献过载 + 导师催 + AI 捷径诱惑 改述为"漏斗"，先提筛选标准，主方案是 VOSviewer / CiteSpace 领域结构图 + Elicit / Consensus / Litmaps 批量摘要 4/4

三个场景的失败模式互不相同，说明这是通用默认行为与钟澄方法的系统性差异，不是偶发失误——所以这个 skill 有存在的必要。

REFACTOR 阶段从 GREEN 结果里反向发现并关闭了一个真实缺口：

缺口由多种材料组成的器件名是一个单元，不能拆成组成元素

skill 原文只说"拆到最小单元"，没有明确说锌镍电池 / 镍氢电池不可拆成 zinc OR nickel。 用户完全可能据"拆到最小单元"四字而误拆——而这是"结果一半不相关 + 标题看不懂"最常见的单一根因。 修补依据全部来自原材料：lithium ion batter* 在锂电案例里是作为一整个检索词测的（标题 34,018 条）， 钙钛矿案例里"光催化"也不拆成"光 / 催化"。

08安装

仓库根目录即 skill 根目录，克隆后软链到 ~/.claude/skills/ 即可被 Claude Code 发现。

# 1. 克隆到任意位置
git clone https://github.com/marxchen7/zhongcheng-literature-search.git

# 2. 软链（Windows 用管理员 PowerShell）
New-Item -ItemType SymbolicLink `
  -Path "$env:USERPROFILE\.claude\skills\zhongcheng-literature-search" `
  -Target "F:\code\zhongcheng-literature-search"

# macOS / Linux
ln -s ~/code/zhongcheng-literature-search ~/.claude/skills/zhongcheng-literature-search

装好后直接提问即可触发，例如："我在写硕士论文，方向是中国钢铁行业低碳转型的政策工具组合与实施顺序，请帮我设计一套 Web of Science 的检索方案。"

方法源自钟澄《科研论》。本仓库是对其文献检索部分的结构化整理与可执行化，案例中的命中量级与原文引述均取自原书。
